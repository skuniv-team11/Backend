# ADR-0033 현장실습 진행: 지원서(제5호)부터 학점 인정 명단까지 한 흐름으로, 체험 계정은 묶음으로 나눈다

- 상태: 확정 (2026-10-10 — 박경원 결정: 새 API 설계안 'P0부터'. v2 프로토타입의 '내 현장실습'·'지원서'·센터 '접수함·매칭·선발·마무리' 화면. PR 병합으로 확정한다)
- 문제
  - 지금 서비스는 지원 전(판정·추천·탐색)과 실습 뒤(커리어)만 있고, 그 사이 — 지원서 제출, 센터 접수·매칭·선발, 마무리 서류 — 는 메일·한글 파일로 따로 돈다. 학생은 지금 어느 단계인지, 무엇을 낼 차례인지 한곳에서 보지 못하고, 센터는 지원서를 메일함에서 모아 손으로 정리한다.
  - v2 프로토타입은 이 흐름을 한 타임라인(학생)과 처리 화면(센터)으로 그렸다. 기관 계정은 없다(기관 값은 센터가 넣는다).
  - 공개 링크 심사(11/2~11/9) 동안 여러 심사위원이 동시에 체험 계정을 쓴다. 센터 화면을 하나로 두면 서로의 시연이 섞인다.
- 결정
  - **일정은 공지 그대로**: 진로취업처 2026-2 학생 모집안내(job.skuniv.ac.kr/notice/8899)의 11단계 날짜를 `curated/round.json` → `round_stage`로 넣는다. 공지에 날짜가 없는 중간점검(8주차로 둠)·학점 인정은 `confirmed: false`로 표시한다(센터 확인 전).
  - **지원서 = 별지 제5호 한 부**(운영서식 2026-2): 신청서 기본정보·학적·1~3지망·이력서·자기소개서 4문항(각 300자 이상)·서약·동의 2개·본인 서명·학과(부)장 승인. 1~3지망은 담은 직무 순위(#22)에서 오고, 낼 때 그때 판정과 학적(저장한 프로필)을 고정한다.
  - **개인정보**: 이름·생년월일·성별·연락처·주소·학번은 개인정보 수집·이용 동의(`consents.collect`) 뒤에만 저장한다(동의 없이는 아무것도 저장하지 않음). 사진·계좌는 받지 않는다(파일 저장소가 없고, 계좌는 서식상 협약 단계). 학과(부)장 승인 화면에는 이름·학번·학과·학년·지망만, 연락처·주소·자기소개서는 보이지 않는다. 탈퇴하면 cascade로 지운다(ADR-0008). 로그에 남기지 않는다.
  - **학과(부)장 승인은 링크로**: 메일을 보내지 않는다(메일 연동 없음). 128비트 무작위 토큰 링크를 학생이 학과 사무실에 전하고, 링크를 연 사람이 승인한다. 승인은 요청 때 내용의 해시에 묶어, 승인 뒤 내용·지망이 바뀌면 `STALE`(다시 요청)로 본다 — 학과장이 본 것과 낸 것이 같게.
  - **센터 흐름**: 접수(보완 요청은 이유 필수) → 1~3지망 중 하나로 매칭(화면은 판정과 상담 이수만 옆에 두고 순위를 매기지 않는다, 정원을 넘어도 됨) → 확정 → 기관이 알려 준 면접 일정·결과 → 대기가 없을 때 알림 → 합격자의 학생 서류(제9호·제7호·제8호 '냄' 표시)·기관 서류(평가표·출근부 '받음' 표시) → 둘 다 받으면 학점 인정 승인 링크 → 모두 되면 학점 인정·장학금 명단 CSV. 파일은 저장하지 않는다(원본은 후기 간담회 때).
  - **수행결과보고서 ↔ 커리어 리포트**: 보고서 '냄'은 매칭된 자리의 커리어 리포트(#34, '실습 내용' → 능력단위)가 있어야 한다. 프로토타입에서 '실제 동작'인 시트가 이것이다. 협약서·중간점검서·학점인정신청서·설문 내용은 체험용 화면이라 저장하지 않는다.
  - **체험 묶음**: 체험 계정을 만들 때 `demoGroup`을 받아 같은 브라우저의 체험 학생·센터를 한 묶음으로 잇는다. 묶음마다 가상 지원자 6명(프로토타입과 같은 값, `virtual: true`)을 새로 만든다. 체험 센터는 자기 묶음만, 가입 센터는 묶음 없는(실제) 지원서만 본다. 묶음은 마지막 체험 계정과 같이 지운다.
  - **체험 시점**: 체험 학생은 `stage`로 기준일을 고른다(지원 중 7/23 · 실습 중 10/14 · 마친 뒤 12/17). 실습 중·마친 뒤는 지난 기록(지원서·승인·접수·1지망 매칭·합격, 마친 뒤는 기관 서류·학점인정신청서·설문)을 `virtual: true`로 갖고 시작한다. 수행결과보고서만은 학생이 직접(커리어 리포트 AI) 낸다.
  - **시연 버튼**(#58): 체험 센터 계정이 묶음을 접수 → 매칭 확정 → 선발 알림 → 마무리까지 한 번에 진행한다(심사위원이 단계를 건너뛰어 볼 수 있게). 가입 계정은 403.
  - **현황판**(#24): '처리할 것'(새 지원서·보완 요청)과 '학생이 찾는 직무'(직무 탐색 1~3위 → NCS 세분류별 학생 수 vs 공고·정원)를 더한다. v2 화면은 관심(담은 수)을 보여 주지 않지만, 필드는 프론트가 옮긴 뒤 뺀다(지금은 더하기만).
  - V11: `round_stage`·`demo_group`·`application`·`application_pick`·`dept_approval`·`internship_close`, `app_user.demo_group_id`·`demo_today`.
- 이유
  - 학생 쪽 타임라인과 센터 처리가 같은 데이터(지원서 상태)를 보면, 센터가 바꾸는 순간 학생 화면이 바뀐다 — 메일로 묻고 답할 일이 준다.
  - 승인·서류는 '받았다'는 사실과 시각만 저장해도 흐름이 돈다. 파일·메일까지 하면 저장소·발송 인프라와 개인정보 보관이 커진다(P1).
  - 묶음을 나누지 않으면 심사위원 A가 매칭을 확정한 화면을 B가 보게 된다.
- 확인
  - `InternshipFlowApiTest`: 체험 학생 지원서 작성(동의 없음 400) → 승인 없이 내면 400(`APPROVAL`) → 승인 링크(공개)·내용 바뀌면 `STALE`·409 → 내기(접수번호 007) → 같은 묶음 센터 접수함 7건·다른 묶음 6건·범위 밖 404 → 보완 요청(이유 필수)·다시 냄 → 매칭(덜 고르면 409)·확정 → 선발(대기면 409)·알림 → 보고서는 커리어 리포트가 있어야(409) → 기관 서류 → 학점 인정 승인 → CSV. 실습 중 체험 학생의 단계·D-5·44일째·7/15주·'7~8주차'. 시연 버튼(가입 센터 403). 입력 형식·신청 기간 밖 409.
  - `InternshipUnitTest`: 단계 나누기(신청 마감 뒤 주말, 협약 기간 안 사전교육, 중간점검 뒤, 간담회 뒤), 주차 칸 읽기, 빠진 칸, 승인 해시, 기관 이름 경고, CSV 수식 막기.
- 남은 것: 진로취업상담(가점 횟수·신청·확정, 프로토타입 '상담')과 센터 기관 서류 올리기(운영계획서 PDF → 추출)는 P1. 메일 알림·지원서 PDF 묶음은 메일·PDF 연동 때. 현황판의 관심 필드와 #23·#27(모집 신호·빈 자리)은 v2 화면이 쓰지 않아 프론트 전환 뒤 정리한다. 탐색 수요는 공고 안에서만 고르므로 공고가 없는 세분류(섭외 공백)는 잡지 못한다.
- 다시 볼 때: 새 회차 일정 공지(round.json stages), 서식 개정(제5호 문항·글자 수), 센터가 실제로 쓸 때(가입 센터 계정 발급·보관 기간), 상담 기능이 들어올 때(`counsel_count`).
